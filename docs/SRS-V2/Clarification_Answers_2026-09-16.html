Bench items

B1

Door interlock

SchematicCodeBench

Sensing path. The external door sensor enters on J17_SSR_LED/DOOR SWITCH pin 2. That node drives R125 (1 kΩ), which commons the control inputs of three CPC-1017N relays on Safety.SchDoc.

RelayLoad inLoad outGates
K1GPIO16SSR_SWITCH_450NM to J20450 nm SSR enable
K2GPIO20SSR_SWITCH_405NM to J17 pin 3405 nm SSR enable
K3HEATER_PWMHEATER_PWM_1 to J19Heater PWM

The CM5 never drives that node. GPIO27 is a passive tap behind D10 with R46 (10 kΩ to 3.3 V) as its only pull-up, and the software sets the pin to input with the internal pull off. The hardware interlock therefore covers UV and heater, and software only observes.

Polarity. Bench-confirmed 2026-07-22 and read again 2026-09-16: pinctrl get 27 reads hi with the door closed.

Grace period in the code.

  • A watchdog checks the door every second. Door open while any output is live starts a countdown of abort_after_sec, default 10 s.
  • If the door closes in time, the process continues.
  • If the countdown expires, every output goes off (heater, UV, cooling, fans, N2, BOFA, damper), Err 6016 is raised, and the status strip stays red until acknowledged or a new process starts.
  • LED and heater enables refuse while the door is not confirmed closed. The relays already cut the drive when the sensor line dropped, so the 10 s grace is software only. DVT-SAF-012 requires UV off within 1 s on the Ophir trace.

Closed by the hardware owner, 2026-09-16. No further bench checks are requested for the door interlock.

B2

UV wavelength routing and GPIO17

SchematicCodeBench

Schematic. Text extraction of all 13 pages confirms no net named GPIO17. GPIO16, GPIO20 and GPIO27 appear on several sheets.

Bench, 2026-09-07. The pin is connected to something on testingcm5. GPIO17 HIGH cuts the 12 V rail of the Door LED driver DIM stage in every SSR combination. GPIO17 LOW with only the 450 nm SSR on gives the door its full 12 V DIM. The old assumption "HIGH = 450 nm" was inverted.

The premise of the question is outdated. Since v0.8.33 and v0.8.39 the code no longer uses GPIO17 as the selector:

ModeGPIO16 450 SSRGPIO20 405 SSRGPIO17LED_SWITCH relay K4
450 nm Bleaching1000
405 nm Cure1101
Idle / safe0000

K4 is driven by TCA6424A P05 through Q28 and switches LED_OUT1/LED_OUT2 at J21_LED_SWITCH. Turn-on order on each wavelength change: all LEDs off, K4 to position with read-back and 0.1 s settle, GPIO17 set and read back, SSR enables, then DIM PWM. Only the Door LED is allowed in 450 nm mode.

Answered by the hardware owner, 2026-09-16: GPIO17 is wired to the PCA9685 (U15) OE pin 23. It is not a wavelength line and never was. OE is the active-low output enable for all 16 PWM channels.

With the code's MODE2 = 0x04 and the datasheet, GPIO17 HIGH forces every chip output to 0 without any I2C traffic. The expected effect per channel follows the code's inversion table. Only the door DIM has been measured.

PCA channelsEffect of GPIO17 HIGH
11 to 14 LED DIM0, LEDs dark. Matches the 2026-09-07 bench result.
6 HEATER_PWM0, heater off
10 BOFA0, BOFA off
0 to 5 fans, 7 LIGHT1, 8 and 9 motor enableBehind inverting stages, so expected full on. Motors stay stopped because their TCA direction pins idle at 0.
  • The wrong-wavelength hazard in the question does not exist. Wavelength is selected by the SSR pair and relay K4, and the code already keeps GPIO17 LOW in every mode.
  • Rename the routing key to a PWM output enable instead of deleting it. Its read-back still proves the PWM stage is enabled.
  • GPIO17 can stop heater PWM and LED DIM without I2C. That makes it a candidate stop path for a hung bus. This is a suggestion, not current behaviour.
  • The legacy HSI row and the components.json comment that call GPIO17 "HIGH = 450 nm" are wrong.
Open (bench): confirm that GPIO17 HIGH drives the fans to full speed and cuts the heater PWM.

TCA fan-enable bits P11 to P16. FANONOFF.SchDoc shows they drive six high-side +12 V switches (Q29 to Q34) to an 8-pin connector J22. They are not in series with the six fan connectors above. Nothing in the software calls them.

Thresholds in the code (policy 2026-09-09). While a fan runs at 30 % duty or more, its RPM is compared with a nominal table. 10 % low for 60 s raises warning 9051. 20 % low for 60 s raises critical 9002, stops all outputs, and names the fan with measured and expected RPM. The heater pre-flight needs FAN_HEATER above 100 RPM. Any LED fan reading 0 RPM blocks UV start (Err 9003).

Answered by the hardware owner, 2026-09-16: nothing is connected to J22. The FAN1..6_ONOFF bits are unused, and the fans are controlled only by PCA9685 PWM and monitored by tach.

B4

BOFA fume extractor

SchematicCode

The code drives only PCA9685 channel 10 (4DA_BOFA_PWM, not inverted) and turns it off on a door abort.

The board has more than the code uses. On Light Sensor.SchDoc:

  • BOFA_EN on GPIO6 (J1 pin 31) switches a fused +24 V branch through Q18/Q19.
  • BOFA_PRESENT comes back through Schmitt buffer U19A, most likely to GPIO18 (J1 pin 12).
  • 4DA ANALOG feeds the op-amp stage that produces the BOFA PWM signal.

A presence input and an enable therefore exist on the PCB. Neither GPIO6 nor GPIO18 appears in the software.

Open (bench and BOFA datasheet): levels on BOFA_EN and BOFA_PRESENT, and the connector semantics.
B5

Pressure sensor and light sensors

BenchCode

The HSI pressure IC is not fitted. An I2C scan on 2026-09-14 found bus 0: 0x23, 0x45, 0x49, 0x55, 0x5d, 0x65, and bus 1: 0x48, 0x49. There is no ABP2 at 0x28, and ADS1115 U8 is also absent, so the legacy kPa placeholder is moot.

The real N2 device is an SMC ISE20-series pressure switch wired from Analog_IN through R86 (120 Ω) to ADS1115 U7 AIN3 on bus 1. It reads 0.52 V without pressure and clamps the ADC with pressure. The code threshold is 2.0 V and the set point is 0.6 MPa, which must match the value programmed on the switch.

Hardware issue raised 2026-09-14: the switch output reaches the 3.3 V ADC input through R86 alone, which overdrives the input clamp. A divider or clamp is needed on Analog_IN.

Light sensors. U10 is present on bus 1, but rev07 has no photo-sensor front end for AIN0/AIN1. Nothing in the product reads them.

Answered by the hardware owner, 2026-09-16: the model is SMC ISE20A-T-01. Decoded from SMC catalog CAT.ES100-114:

CodeMeaning
ISE20APositive pressure, rated −0.100 to 1.000 MPa, IP40, 12 to 24 VDC
TPNP open collector, 2 outputs, plus analog voltage output 1 to 5 V with about 1 kΩ output impedance
01R1/8 port, no lead wire included

Lead colours: brown DC+, blue DC−, black OUT1 (PNP), white OUT2 (PNP), gray analog. The code's analog mode matches this model: 0 MPa is 1.364 V and 6 bar is 3.545 V.

The 2026-09-14 reading does not fit the gray lead. A powered 1 to 5 V output never reads 0.52 V, and 5 V through 1 kΩ cannot overload the ADC. About 0.5 V without pressure and a clamped ADC with pressure fit a PNP switch output, which swings to 11 to 23 V into the 3.3 V ADC.

  • If a PNP output (black or white) is on Analog_IN: the software must run switch mode, and a divider or clamp is mandatory to protect U7.
  • If the gray lead goes to Analog_IN: analog mode is right, but without a 2:1 divider the input saturates near 0.5 MPa, so the 6 bar guard never reads a value.
Open: which lead colour is on Analog_IN, and whether the switch was powered during the 0.52 V reading (bench). Light sensors in v1 or later (PO).
B6

NFC reader

BenchCode

The working reader is a USB device, not the board header. An Eccel Pepper C2 on USB (0483:5740, /dev/ttyACM0, 115200 binary protocol, firmware 1.14) read a tag UID on 2026-09-14. The server detects it by USB identity and raises an error when it is missing.

The C2 only listens after a line-coding change, so every open sets 9600 and then 115200.

The board's own NFC path (J15_UART_NFC with SPI level shifters, NFC_CS on GPIO4, NFC_INT on GPIO7) is unused. Only the 10 ms reset pulse on TCA P01 is implemented.

Answered by the hardware owner, 2026-09-16: the NFC reader connects over USB. The v1 NFC scope is the USB Pepper C2. The J15 SPI path and the TCA reset pulse are out of scope, because that reset line goes to the unused J15 header.

B9

OTA mechanism and bundled services

CodeBench

Legacy update path: USB only. A .scu file holds a payload tarball and a signature. The updater verifies it with openssl against an RSA public key, runs install.sh --pre and --post, and calls install.sh --rollback on failure. There is no GCP bucket code in the repository.

Reference unit, 2026-09-16: no SWUpdate, no RAUC, no motion, and USB is in host mode rather than Ethernet gadget.

NetBird is also installed, enabled and running on the test unit, next to a VNC server. So it is not unique to origin.img.

The team's own secure-appliance design chose RAUC with A/B slots, while origin.img ships SWUpdate. One mechanism has to be chosen before Epic 7 (see PO-9).

Open (David/Roman): who installed NetBird and why, and which update mechanism is the target.
B10

Touchscreen and USB topology

Bench

Reference unit display: Raspberry Pi Touch Display 2, 7", on DSI-2 (native 720×1280, rotated 270°). Touch is a Goodix GT911 at 0x5d on i2c-0, with the panel controller at 0x45. The touch panel therefore shares bus 0 with the TCA, PCA and ADS U6. The kiosk runs lightdm and Chromium.

Divergence. The C# port targets the 10.1" Touch Display 2 instead. That panel needs its own power supply.

USB: five root hubs and one 4-port QinHeng hub on the carrier, with nothing attached at read-out. The software uses USB for the NFC reader, a USB stick for updates and exports, and the Ophir and Pico TC-08 meters for DVT only.

Open (PO): 7" or 10.1" for production.

B12

Damper servo

CodeSchematic

GPIO8 (J1 pin 24) goes through an inverting stage R91/Q16 to J2_MOTOR_DAMPER. Pulses are 0.5 to 2.4 ms, pre-inverted in software, and generated by the RP1 PIO block for jitter-free timing. The pulse is held 1.5 s after each move. Cooling opens at 0° and closes at 90°.

Answered by the hardware owner, 2026-09-16: the servo is an MG90S. The configuration is right and the HSI entry "SG90" is wrong. There is no read-back, so the servo is never a safety precondition.

Closed by the hardware owner, 2026-09-16. The answer is confirmed as complete. No further bench checks are requested for the damper servo.

PO-4

Device name validation

CodeOpen

The SRS proposes default "S-Cure" (OI-7) and specifies only "non-empty" (OI-8). The code trims the input and requires it to be non-empty. It sets no length limit, character set or uniqueness rule, and stores the name in browser local storage with default "sCure".

Story 2.1's "1 to 64 printable characters, no default" is stricter than both the SRS and the code.

PO-5

Timer start and UV start

CodeOpen

The SRS contradicts itself, and the code matches only part of it:

  • SRS §6.7 defines TimerMode (on-ramp or on-target) and UVStart (at-start or at-target), both defaulting to "at temperature".
  • OI-16 says the runtime never branches on them. That is still true: the cure screen always ramps first and then starts the countdown.
  • OI-17 says these fields were removed, but the code still carries them in the editor, the CSV header and validation.

Accurate legacy characterization for the fixtures: the fields are captured and validated, and the runtime always behaves as on-target and at-target.

PO-8

Organization Link

CodeOpen

The code reads the CSV as plain text and takes the first match of this case-insensitive, unanchored pattern:

/[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}/i

There is no RFC 4122 version or variant check and no case normalization. The ID is stored as matched in browser local storage. No CSV schema exists (SRS OI-10). The organization ID is never sent to the cloud (OI-11), because the sync snapshot does not include it. A file without a match raises Err 5001.

PO-9

Update delivery, C1 to C7

CodeOpen

Answers from the legacy software:

C1File level. A payload tarball is installed into /opt/scure by install.sh.
C2Script-level rollback with install.sh --rollback. No A/B partitions.
C3An RSA public key shipped in the repository, checked with openssl dgst -sha256. The matching private key is also in the repository (see the security note at the top).

C5No device identity for updates. The cloud agent uses a per-machine key and is outbound-only.
C6, C7Open, for the PO and the customer.

There are now three incompatible candidates: the legacy .scu path, RAUC A/B from the appliance design, and SWUpdate A/B in origin.img. Which one is "the customer's existing infrastructure" is the question for David and Roman.

PO-10

CodeOpen

SRS §6.4 and the code agree. Cure Together is allowed for one print or several prints of the same material, compared by name. Different materials are blocked with "Cannot cure different materials together!". The rule for positions and trays beyond name equality is still open as OI-15.

PO-12

Cloud inbound writes

CodeOpen

The legacy cloud agent is outbound-only by design and has no hardware commands. About every 10 s it posts a snapshot to /api/agent/sync with a machine key. It applies a small set of commands returned in the response, such as saving a program, and acknowledges them on the next sync. The agent stays off unless a cloud config file exists, and it does not exist on the reference unit. Customer confirmation is still needed.
