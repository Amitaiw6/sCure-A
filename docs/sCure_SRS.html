1. Introduction & System Overview

1.1 Purpose

The sCure Box is a post-processing unit that complements the Origin printer. It is part of the manufacturing process: it takes a printed resin part and brings it to a finished, ready-to-use state through a controlled, repeatable post-process run from a stored Material (program).

The system is designed to ensure:

  • Optimal mechanical properties of the printed parts.
  • Maximum accuracy obtained from the printer.
  • A uniform and consistent workflow.
  • A complete, high-quality post-process for the user, with a record (cure report) of every run.

This revision of the SRS specifies the behavior of the sCure CS firmware, version 1.0.106 (touchscreen UI and machine firmware running on the unit). Where this document and the firmware differ, the difference is listed as an Open Issue (§12).

1.2 Core Mechanisms

A Material is an ordered list of steps. Each step uses one of six process types; the unit executes the steps one after another as a single, uninterrupted run, from the moment the part is loaded and the run is started until the part is ready for use. The process types are:

#Process (UI name)Role in the workflowThe step ends when
1DryingHeats the chamber to a low target temperature with the damper closed; once the target is reached the damper opens and the chamber intake fan runs, so moisture is vented while the temperature is held.The target is reached and the step's hold time has elapsed.
2HeatingHeats the chamber to the target temperature (damper closed) and holds it.The target is reached and the step's hold time has elapsed.
3CureExposes the part to 405 nm UV light at the step's UV intensity, normally at a chamber target temperature. A Cure step without a temperature is UV-only (no heating).The step's hold time has elapsed (counted from the target being reached, or from the step start, as the step specifies).
4BleachingAs Cure, with 450 nm light.As Cure.
5NitrogenPurges the chamber with nitrogen (N2). Nitrogen steps are executed only when Nitrogen Mode is switched on in Settings (§11); otherwise they are skipped.A fixed purge time has elapsed.
6CoolingSwitches UV and heating off, opens the damper and runs the fans to bring the chamber down at the selected rate (Fast / Medium / Slow).The chamber has reached the step's target temperature.

The step parameters and their limits (temperature, hold time, UV intensity, cooling rate, timer start / UV start) are defined with the Material editor (§6), and the run-time sequencing, transition rules, pause / resume / abort and supervision are specified in the Cure Process section (§7). Throughout a run, and also when the unit is idle, the firmware supervises the door, the temperature sensors, the fans and the UV LED panels, and stops the outputs on a fault (§7, §9).

At every power-on the unit runs a boot self-test (door, temperature sensors, 405 nm and 450 nm UV LEDs, chamber fans, firmware API) before the Setup or Home screen is shown (§3.3.1).

1.3 Connectivity & Monitoring

The unit gives the user continuous access to the state of the process on its own touchscreen (Cure Process, Cure History and Alerts screens, §7–§9). When a cloud connection is configured on the unit, the firmware also synchronizes with sCure Cloud at a regular interval, so the process can be monitored remotely from start to end. The synchronized information includes:

  • System state (chamber temperature, door, heating / cooling / UV status, internet status, component run-time counters).
  • The user Materials (programs).
  • Recent prints and recent cure runs (summaries, without the full telemetry).
  • Alerts and errors raised and cleared during the last 48 hours.

sCure Cloud may send data-only commands back (add / update / delete a Material, send a print); the cloud has no command that actuates the hardware. A DVT test requested from sCure Cloud runs only after the operator confirms it with Start on the unit's screen. Deleting a cure run on the unit also deletes its report from sCure Cloud. [GrabCAD presentation — Open Issue OI-29]

3. Setup Screen

3.1 Purpose

The Setup screen performs the first-run configuration of the unit. It is a full-screen wizard that is responsible for:

  • Recording the unit's Serial Number (SN) by scanning its barcode label, when the unit does not have one yet (§3.3.4).
  • Naming the unit (Name step, §4).
  • Linking the unit to an organization, or skipping that (Link Organization step, §5).
  • Saving the configuration and marking Setup as complete.
  • Creating a positive first-use experience, giving the user the feeling of being the first to open the device.

Setup is shown after the boot self-test whenever Setup has not been completed (§3.3.2). After Setup completes, the user is taken to the Home screen (§6). In sCure CS 1.0.106 Setup does not contact sCure Cloud: there is no cloud SN assignment and no cloud registration step [OI-30].

Source: sCureBox-CS/src/SCureBox.Ui/ViewModels/Pages/SetupViewModel.cs, BootViewModel.cs, Services/BootSelfTest.cs, Services/BarcodeScanner.cs, Services/UiSettingsStore.cs.

3.2 Interface Reference

The visual layout of the Setup screen and the Get Started entry point are defined in the reference HTML file (sCure-UI.html), which is the source of truth for the screen. This section specifies only the Setup logic. Once the user leaves the Welcome step, a step indicator shows the Setup steps; the Serial Number step appears in it only when that step is needed.

3.3 Setup Process

The process starts at power-on with the boot self-test, then decides between Setup and Home, and — for Setup — proceeds through the ordered steps below.

3.3.1 Step 0 — Power-on boot self-test

At every start of the firmware the Boot screen shows the logo and then runs the following checks, one after another, in this order:

#Check (UI label)Passes whenOn failure the screen shows
1Door ClosedThe door sensor reads closed. While the door is open the screen shows "Close the door to continue" and waits up to 60 s."The door is open - close it and retry", or "The door sensor is not reading".
2Temperature SensorsEvery supervised temperature sensor (chamber and LED panel sensors) and both side-panel sensors give a valid reading; the check waits up to 5 s after start-up for the first reading."Not reading: <sensor list>".
3UV LEDs 405nmThe 405 nm panels are lit for 15 s and the panels warm up by at least 0.8 °C (same test as the Settings LED Test, §11).The LED test's message, or "The LED test failed".
4UV LEDs 450nmAs check 3 for the 450 nm panels, lit for 30 s.As check 3.
5Chamber FansNo fan fails the fan test (Settings fan test, all fans, §11). A fan rated "worn" (warning) still passes."Not spinning: <fan (RPM)> …", or "The fan test failed".
6API ServerThe firmware's state interface answers."The firmware API is not answering".

Rules:

  • The UV LED checks (3, 4) shall run only when check 1 passed. With the door not closed they are reported as failed with "Skipped - the door is not closed"; no UV light is switched on.
  • Planned restart: when the previous firmware stop was clean (reboot from Settings, software update, firmware self-restart) and happened at most 10 minutes before the start, checks 3, 4 and 5 are passed without being run, so the unit is back within seconds. After a power loss, crash or watchdog stop (no clean stop recorded) the full self-test runs.
  • When no IO board is present (simulation), checks 2–5 pass immediately.
  • A check that cannot run is reported as failed ("The check could not run: …").
  • When all checks pass, the screen shows "All systems operational" and proceeds by itself to the Setup gate (§3.3.2).
  • When one or more checks fail, the screen stays on the result ("<n> of 6 checks failed", with the reason per check) and offers Retry (runs all checks again, without the logo) and Continue anyway (proceeds to the Setup gate despite the failures). A failed self-test does not lock the unit and raises no alert. [OI-33]

3.3.2 Step 0b — Setup gate

After the self-test the system reads setupComplete (§3.5): the value saved on the machine, otherwise the factory value in the system identity file.

  • If Setup is complete → the system shows the Home screen (§6).
  • If Setup is not complete → the system shows the Setup Welcome step (§3.3.3).

Setup is shown again when the user unlinks the organization in Settings, which clears organizationId and setupComplete (§5.3.7, §11). The SN and the System Name are kept, so a repeated Setup skips the Serial Number step and pre-fills the name.

3.3.3 Step 1 — Welcome

The Welcome step greets the user ("Congratulations on your new sCure curing system. Let's set it up in just a few steps.") and offers Get Started. When the user presses Get Started, the system checks whether an SN is already stored (§3.5: the SN saved on the machine, otherwise the SN in the system identity file):

  • If an SN is stored → the Serial Number step is skipped and the Name step (§4) is shown.
  • If no SN is stored → the Serial Number step (§3.3.4) is shown.

3.3.4 Step 2 — Serial Number

The Serial Number step records the unit's SN from the barcode label using a USB barcode scanner.

  • The step shall wait for a scan ("Scan the barcode" / "Waiting for the scanner..."). A scanner connected while the step is shown shall be detected automatically.
  • A scanned code is accepted only while this step is on screen. A valid SN is 3–40 characters: letters and digits, and after the first character also . _ / -. Surrounding spaces are removed.
  • On a valid scan the step shows "Serial number scanned" with the SN, and Next becomes enabled. Scanning again replaces the SN.
  • On an invalid code the step shows "<code> is not a valid serial number" (the code shortened to 40 characters) and keeps waiting; an SN accepted earlier in the step is kept.
  • The step cannot be skipped: Next stays disabled until a valid SN has been scanned (or typed, below). There is no way back to the Welcome step from it.
  • Manual entry (service): ten taps on the barcode label picture open the device-password pad. With the correct password the SN field opens the on-screen keyboard so the SN can be typed; the same validity rule applies. Entering the password here does not leave Developer Mode switched on.
  • On Next the SN is saved on the machine (§3.5) and the Name step (§4) is shown. From then on the SN is shown in Settings and written into every cure run and cure report.

The SN cannot be changed later from the UI. [SN uniqueness / later change — OI-30]

3.3.5 Steps 3 and 4 — Name and Link Organization

The Name step is specified in §4 and the Link Organization step in §5. Setup ends on the Link Organization step, which marks Setup as complete and shows the Home screen.

3.3.6 Steps of earlier revisions not performed by sCure CS

sCure CS 1.0.106 does not restore the SN from an SD backup, does not check the internet connection, does not request the SN from a cloud service and does not register the unit in a cloud during Setup. The registry entries 3001 (Serial Number Restore Failed), 3002 (Cloud Communication Failed) and 3003 (No Internet Connection) are therefore never raised. [Open Issue OI-30]

3.5 Configuration Storage

The values set during Setup are kept on the unit's storage in two files. A value saved on the machine always takes precedence over the factory value.

4. Setup Name Screen

4.1 Purpose

The Name step of Setup lets the user assign a human-readable name, the System Name, to the unit. The user reaches it after Get Started (§3.3.3), or after the Serial Number step when that step is shown (§3.3.4). The name identifies the unit:

  • In the local interface (top bar, Settings, the Link Organization subtitle).
  • In cure runs and cure reports.
  • For convenient identification of the device in the lab when several units are present.

The System Name is not sent to sCure Cloud in sCure CS 1.0.106. [OI-32]

4.2 Interface Reference

The visual layout of the Setup Name screen is defined in the reference HTML file (sCure-UI.html), which is the source of truth for the screen. This section specifies only the logic.

The step presents the title Name Your Cure Box, the hint "Choose a name to identify this device", a Device Name field and a Next button. The field is pre-filled with the saved System Name, or with the default sCure when none has been saved (resolves OI-7). An illustration of the unit shows the name as it is typed.

4.3 Screen Logic

4.3.1 Step 1 — Display the name field

The system displays the Device Name field pre-filled as above; Next is enabled at once, so the default can be accepted without typing.

4.3.2 Step 2 — Text entry

When the user taps the name field, the system opens the on-screen keyboard with the current name. Closing the keyboard keeps the text typed so far.

4.3.3 Step 3 — Validation

  • If the name is empty or consists of spaces only → Next is disabled and the field shows "Tap to enter name...".
  • Otherwise → Next is enabled. No further rule (length, allowed characters, uniqueness) is applied. [Open Issue OI-8]

4.3.4 Step 4 — On Next

When the user presses Next, the system:

  1. Removes leading and trailing spaces and saves the name as the System Name in the UI settings file (§3.5).
  2. Proceeds to the Link Organization step (§5).

The name is saved again when Setup finishes on the Link Organization step.

5. Connect Organization Screen

Status. The Link Organization step is implemented in sCure CS 1.0.106 with two ways to obtain the organization: a CSV file on a USB drive and sign-in on the Origin website. Still open: the CSV schema (OI-10), propagation of organizationId to sCure Cloud (OI-32) and the sign-in methods available on the unit (OI-34).

5.1 Purpose

The Link Organization step (UI title Link Organization) is the final Setup step. It links the unit to the user's Origin organization so the unit is associated with the correct organizational account. The user may also skip this step and continue without an organization. Without an organization, the Home screen does not show print history (§6).

5.2 Interface Reference

The visual layout of the Connect Organization screen is defined in the reference HTML file (sCure-UI.html), which is the source of truth for the screen. This section specifies only the logic.

5.3 Screen Logic

5.3.1 Step 1 — Display the options

The step presents the title Link Organization and the subtitle Link <System Name> to your organization, together with:

  • Upload Organization CSV ("Select the CSV file from the USB drive").
  • Sign in to Origin ("Use your Origin account").
  • A Link Organization button, disabled until an organization has been found.
  • Continue without organization.

The two source options are hidden while an organization is shown as found.

5.3.2 Step 2a — Upload and read the CSV

When the user taps Upload Organization CSV, a USB file browser opens ("Select organization CSV"). It lists the .csv files on every mounted USB drive, in the drive's root folder and up to two folder levels below it (hidden folders are skipped; at most 200 files). With no CSV file on any USB drive it shows "No CSV file found on a USB drive". Closing the browser without a choice leaves the step unchanged.

The system reads the chosen file as text and searches it for an Organization ID — a UUID (hexadecimal, format 8-4-4-4-12, upper or lower case). The first UUID found anywhere in the file is taken [CSV schema — Open Issue OI-10].

  • If a UUID is found → the step shows "Organization Found" with the ID and "from <file name>", and Link Organization becomes enabled.
  • If no UUID is found, or the file cannot be read → the message "No valid organization ID found in CSV file" is shown; no Organization ID is set and Link Organization stays disabled. The user may select another file.

5.3.3 Step 2b — Sign in to Origin

When the user taps Sign in to Origin, the system opens the Origin website (app.origin.io, the sign-in address configured on the unit) inside a Sign in to Origin dialog. The user signs in on the website as on a computer; tapping a text field of the website opens the on-screen keyboard (password fields are masked).

  • The system shall take only the organization (its organizationId UUID, and the account name / e-mail for display) from the signed-in website. Nothing about the sign-in is stored on the unit: each sign-in uses a new, empty browser profile that is deleted afterwards. The dialog states "Only the organization is taken from your account. Nothing about your sign-in is stored on this machine."
  • On success the dialog closes and the step shows "Organization Found" with the ID and "from Origin account <e-mail or name>"; Link Organization becomes enabled.
  • If the sign-in does not finish within the configured time (default 300 s, limited to 30–1800 s) the dialog shows "Sign-in took too long - try again". Other failures show "Origin sign-in failed - try again", "No web browser found on this machine" or "Origin sign-in is not set up on this machine". The user can choose Try Again or cancel; cancelling leaves the step unchanged.

The Origin sign-in needs an internet connection; the step does not check the connection beforehand. [Sign-in methods on the unit — OI-34]

5.3.4 Step 2c — Change

While an organization is shown as found, Change clears it so the user can choose a source again.

5.3.5 Step 3 — Link the organization

When the user presses Link Organization (enabled only when an Organization ID is found), the system saves the System Name, sets organizationId, marks Setup as complete (setupComplete = true), persists the configuration (§5.4) and shows the Home screen.

5.3.6 Step 4 — Continue without organization

The user may skip this step. The system marks Setup complete without an Organization ID (organizationId is saved empty), persists the configuration and shows the Home screen.

5.3.7 Later changes (Settings)

An organization is optional. It may be linked or changed later from the Settings screen, with the same two sources (CSV on a USB drive, Sign in to Origin) and the same UUID rule (§11). Unlink in Settings clears organizationId and setupComplete and opens Setup again (§3.3.2). organizationId is not sent to sCure Cloud in sCure CS 1.0.106. [OI-32]

6. Home Screen

6.1 Purpose & General Page Behavior

The Home screen is the system's main hub — the central page from which the operator oversees and runs all of the sCure Box's work. It is shown once onboarding is complete and is the entry point for normal, day-to-day operation. From Home the operator can:

  • review the box's recent work — the recent prints handed to the box for finishing;
  • manage the library of curing programs (Materials) — both the programs provided by the system (built-in presets) and the operator's own user programs;
  • define the curing process to run, by creating, importing, duplicating or editing a program — setting its steps, parameters and options; and
  • select a program and start the cure.

In short, Home is where the operator decides which curing process to run — choosing one of the programs provided by the system or defining their own — and launches it.

Main areas. (1) the persistent top bar — status & navigation (§6.3); (2) the Recent Prints list (§6.4); (3) the Program List — the material programs (§6.5); (4) the floating Start Cure action (§6.7, §6.8).

Default state on load. Every time Home is shown, its state is rebuilt: the program list is re-read (presets + user programs, favorites first), the favorites and the organization link are re-read, and the recent prints are re-read. No program and no print is pre-selected — a selection made earlier is not kept when the operator leaves Home and comes back (for example after a cure). While the programs load the list shows "Loading materials...".

When the page is ready to proceed. The page can start a cure when a program is active: a program row is selected, or a recent print is selected and its material name resolves to a program (§6.4). Start Cure is shown as disabled (grey) whenever no program is active, the chamber door is open, or a critical alert is active; the exact gates and what a press does in each case are in §6.7 and §6.8.

Empty / missing data.

  • No organization linked → Recent Prints shows the "No organization" card and View All is hidden (§6.4); the Program List and Start Cure are unaffected.
  • No recent prints (organization linked, empty history) → "No prints yet."
  • No programs → "No materials yet. Upload a CSV or create a new material."; the Edit button is hidden and Start Cure stays disabled.

Dependencies. The Program List depends on the material store (PostgreSQL when the database is available, otherwise the JSON files — §10.1); Recent Prints depend on the print-history store and on the organization link; favorites, the organization link and Nitrogen Mode come from the unit's UI settings (ui-settings.json, §10); the Start Cure gates depend on the machine state (door, refreshed about once per second) and on the active alerts (§9). Displaying the page and starting a cure require no live printer connection and no cloud call. Source: src/SCureBox.Ui/ViewModels/Pages/HomeViewModel.cs.

6.4 Recent Prints

Purpose. Recent Prints surfaces the most recent prints handed to the box directly on the Home screen, so the operator can see and select a recent print at a glance — without opening the full Print History. The complete list is available via View All (§6.4.1).

Data source & persistence. The list comes from the on-device print-history store, not from a live cloud call. The same store is exposed on the local API as GET /api/print-history and replaced as a whole by POST /api/print-history. The data persists across application restart and reboot.

Where entries come from. In CS 1.0.106 a print entry is created (a) by the cloud portal's send_print command — the new entry is put at the front of the history (§10.6) — or (b) by a full replace through POST /api/print-history. The box does not add a print entry when a cure finishes; instead, prints cured through View All are removed from the history when that cure completes (§6.4.1). 6.7.2 Step Types, Parameters & Sequencing

This is the reference for the step fields, limits and sequence rules. The same program rules are applied by the editor (live clamping + Save), by CSV import (§6.7.4) and, at Start, by the machine (§6.8, with one relaxation noted below). Source: src/SCureBox.Domain/Programs/ProgramValidator.cs, src/SCureBox.Ui/ViewModels/Editor/EditorRules.cs, StepCardViewModel.cs.

Processes offered (in this order): Drying · Heating · Cure (405 nm) · Bleaching (450 nm) · Cooling · N₂ Purge.

Fields per process (exactly the fields a step card shows):

  • Heating — Process · Temperature · Time.
  • Drying — Process · Temperature · Time.
  • Cure (405 nm) — Process · Chamber Heating (On / Off) · Temperature, Timer Start and UV Start (only with Chamber Heating On) · Time · UV Intensity.
  • Bleaching (450 nm) — as Cure.
  • Cooling — Process · Target Temp · Cooling Mode (no Time).
  • N₂ Purge — Process only, with the note "The N₂ purge runs automatically if nitrogen is enabled; otherwise it is skipped."

Value entry. Values are whole numbers. The −/+ buttons move temperature by 5 °C, time by 1 min and UV intensity by 5 %; the number pad accepts any whole value inside the field's current range (it is not limited to multiples of 5).

Defaults. A step added with Add Step is Heating 40 °C / 10 min (raised to the running minimum when that is higher, capped at the process maximum); a forced Cure is 40 °C (or the running minimum) / 10 min / UV 30 % / Timer Start and UV Start At temperature; a forced Cooling is 30 °C (capped at the cooling ceiling), Medium. Switching a step to Cooling sets its target to 30 °C (capped at the ceiling); switching from Cooling to another process sets 40 °C (or the running minimum). Chamber Heating defaults to On.

Timer Start & UV Start (Cure / Bleaching with Chamber Heating On).

  • Timer Start — At temperature (on-target, default): the step's time starts when the target temperature is reached. On ramp start (on-ramp): the step's time starts with the heat-up ramp.
  • UV Start — At temperature (at-target, default): the UV turns on when the target temperature is reached. On ramp start (at-start): the UV turns on at the start of the ramp.

Both are stored on the step and in the CSV (TimerMode / UVStart) and are applied by the cure execution (§7). With Chamber Heating Off the step has no temperature, no Timer Start and no UV Start (UV only); a Ventilation value of such a step, when the program came from a CSV or an older program, is kept unchanged — the editor offers no field for it.

Sequencing — what may come after what.

  • After an N₂ Purge → only Cure or Bleaching.
  • After the Cure/Bleaching that follows an N₂ Purge → only Cooling (the vent).
  • N₂ Purge placement. A purge is offered only while fewer than 2 purges precede the position and a Cooling step has occurred since the previous purge (the first purge needs no Cooling before it). At most 2 N₂ purges per program.
  • Running minimum. A heated step (Heating, Drying, Cure/Bleaching with heating On) may not ask for a lower temperature than the last heated step since the most recent Cooling. N₂ steps and UV-only steps do not change it; a Cooling step resets it to 30 °C. Lowering a step's temperature in the editor raises the following heated steps to match.
  • Drying cap. Drying never goes above 50 °C. A Drying step after a hotter heated step therefore cannot meet the running minimum; the editor shows it at 50 °C and Save reports "Temperature (50°C) cannot be lower than the previous step (…°C) without a Cooling step" until a Cooling step is placed before it.
  • Cooling target. A Cooling target must be at least 5 °C below the temperature of the last heated step.

State machine — allowed step transitions. The same sequencing rules as a state machine, each process drawn as its own state with its parameter limits. 6.7.3 Program Time Estimate

The "~N min" of each Program List row, the editor's "~T min total" and the stored totalDuration are the program's estimated real length, in whole minutes rounded up. Source: src/SCureBox.Domain/Programs/ProgramEstimator.cs.

  • The program is assumed to start at 25 °C; the chamber temperature is carried through the steps.
  • Heated steps (Heating, Drying, Cure/Bleaching with a temperature) add the heat-up ramp from the carried temperature to the target plus the hold time. Ramp rates: 13 s/°C up to 45 °C, 50 s/°C from 45 to 75 °C, 80 s/°C above 75 °C (no ramp when the target is not higher). With Timer Start On ramp start only the part of the ramp longer than the hold time is added. UV-only steps add their hold time only.
  • Cooling adds the time to fall from the carried temperature to the target at 2.5 °C/min (Fast), 1.5 °C/min (Medium) or 0.8 °C/min (Slow); a blank target counts as 25 °C.
  • N₂ Purge adds 120 s.

The Program List and the editor always include the 120 s per N₂ purge; the Cure Process screen (§7) estimates the program as it will actually run — without the N₂ steps when Nitrogen Mode is off. [OI-40]

Parsing rules.

  • A leading UTF-8 byte-order mark and CRLF line ends are accepted; blank lines are skipped. Fewer than two lines → "CSV must have a header row and at least one data row"; a header without Step or Process → "Missing required header: "Step" or "Process"".

  • Blank values: a blank temperature becomes 40 °C on heated rows and 25 °C on a Cooling row; a blank UV intensity becomes 30 %; an unknown or blank cooling mode becomes Medium; an unknown Timer/UV start leaves the default (At temperature). [a blank Cooling temperature therefore always fails the 30–75 °C rule — OI-41]

7. Cure Process Screen

7.1 Purpose

The live curing run. Opened by Start Cure (§6.8), the screen hands the active program to the firmware, which sequences it step by step (Heating, Drying, Cure, Bleaching, Cooling, N₂ Purge) on its own once-per-second loop. The screen shows the run (header progress, one card per step, live gauges), lets the operator pause, continue or abort, reacts to faults the machine reports during the run, and ends in completion (with the cure report) or in an abort / error. The firmware records the run, its alerts, its telemetry and a timing record per step in the cure history (§8). Source: src/SCureBox.Ui/ViewModels/Pages/CureProcessViewModel.cs, src/SCureBox.Application/Recipe/RecipeRunner.cs, src/SCureBox.Domain/Control/RecipeStateMachine.cs.

7.3 Process Logic

7.3.1 Run lifecycle

A run is owned by the firmware, not by the screen. The firmware advances it once per second and reports its state, the current step, the phase of that step and its clocks; the screen renders that status on every refresh (1 Hz).

7.3.2 Entry and start

  • Entry. Reached only from Start Cure (§6.8), after its own gates (no critical alert, door closed, fan pre-check passed or overridden). The screen receives the active program and, for a Cure Together batch, the ids of the pending print-history rows.
  • Steps run. When Nitrogen Mode is off (Settings) the N₂ Purge steps are removed from the program before it is started; they get no card and are not executed. The remaining steps are started as one run.
  • Start. The screen acknowledges a door abort still latched from an earlier run, creates a run id and starts the run. The start answers only after the first step's own checks (pre-flight, heater-fan spin-up — several seconds), so it runs off the display thread: the screen stays live and the "Running System Pre-Check" spinner opened on Home stays up until the run's first status is shown (at most 45 s).
  • Start refused. A refusal is shown as Hardware: <message> and raised on the Alerts screen with its code. A temperature-sensor refusal (9010–9012) or a frozen-reading refusal (9006) opens the heater-fault dialog with Retry (starts again) and Cancel (back to Home); any other code opens a message with the code's registry description and then returns to Home.

7.3.5 Operator actions — Pause, Continue, Abort, Skip

  • Pause. The Pause button on the active card (only while running and no other dialog is open) opens "Pause the Process?": heating, UV and gas stop and the door is released; the step is held and continues exactly where it stopped. It carries the note that pausing may affect the quality of the models (surface finish, shape, dimensional accuracy) and the hot-surface caution (below). Buttons: Keep Running / Pause & Open Door. On confirm: (1) the firmware pauses the run — UV off, heater element off, N₂ valve closed, cooling and ventilation stopped, damper closed; the heater fan is released from the run and gets the normal heater-fan run-on (30 % for up to 15 min, §7.4) — and freezes every clock of the run; (2) the door magnet is released for 2 s; (3) the full-screen "Process Paused — Door Released" overlay shows the step on hold, the hot-surface caution and a door gate line. Continue is enabled only while the door sensor reads closed (also when the machine state cannot be read); Stop Process aborts the run.
  • Continue. The firmware shifts every clock of the run by the pause length, takes the heater fan back to its run duty and re-issues the current step's command: Heating, Drying and Cooling their command again, a Cure / Bleaching step heater + UV if its UV was already lit (or it is UV-only), heater only if it was still waiting for the target, an N₂ Purge re-opens the valve. The re-issued command passes the step pre-flight again (§7.4); if it is refused the run fails. Paused time is excluded from the step timers, the phase-timing records, the overall progress and the completion total time.
  • Abort. The Abort button on the active card (after the run has ended the same button only returns to Home) opens "Stop the Cure Process?": stopping ends the cycle immediately and cannot be resumed (Pause is pointed to for a temporary stop); warnings (1) the model's appearance and surface finish may be affected and (2) a partially cured model may warp or lose its shape and dimensional accuracy; plus the hot-surface caution. Buttons: Keep Running / Yes, Stop. Confirming — or Stop / Abort in any of the dialogs of §7.3.6 — aborts the run: every cure output is stopped (the heater fan gets its run-on), the run ends aborted without an error code, fan overrides granted during the run are withdrawn and the screen returns to Home (see OI-46).
  • Hot-surface caution. In the Pause, Paused and Abort dialogs: at a chamber temperature of 40 °C or more "Caution — hot surfaces inside. The chamber is at <t>°C. Wear heat-resistant gloves and avoid contact with the chamber and the model."; below 40 °C "Caution — hot surface. The chamber and the model may still be warm — wear gloves when handling."
  • Skip. Skipping the current step (it ends now with its timing record and the next step begins; on the last step the run completes) is available over the HTTP API only — the screen has no Skip button.
  • Leaving the screen. If the Cure Process screen is left while its run is still preflight, running or paused, the run is aborted. A run aborted from elsewhere (API) takes the screen back to Home.

7.3.7 Completion

  • When the run reports completed the status bar reads Cure complete! and the "Cure Complete!" overlay opens: "The curing process for <material> has been completed successfully.", Total time (run time, pauses excluded) and the number of steps, with a single Open Door button.
  • In parallel the cure report of the run is built from its telemetry (no telemetry → no report), saved with the run and exported to a USB drive when one is present; on a successful export the overlay adds "Saved to USB" (silent otherwise). Report content and later export: §8.
  • Open Door: if the run was a Cure Together batch (§6.4.1) its pending print-history rows are deleted; the door magnet is released for 2 s (UV and heater are switched off first) and the screen returns to Home. The heater fan continues its run-on after the run (§7.4).

Step pre-flight (every Heat, Dry, Cure UV, UV only and Cool command): (1) a fan latched critical and not overridden refuses the step with that fan's code (9020–9025); (2) a latched frozen-reading fault refuses it with 9006; (3) the required thermistors — chamber, Left LED, Right LED — must read a valid temperature (−20…120 °C), three reads 0.5 s apart, else the step is refused with the first open sensor's code (9010 / 9011 / 9012) and the alert is raised at once; (4) Dry and Cool: the chamber cooling fan is spun at 100 % for 1.5 s and must read at least fan_health.led_fan_min_rpm (100 RPM) over 0.5 s, else refused with 9034 (skipped while cooling already drives that fan, when it is overridden, and for 30 s after a pass); (5) commands that light UV: every LED fan of the panels about to be lit is spun up the same way, else refused with the first failing fan's code (9030–9033, one alert per fan) — skipped while UV is already on and for 30 s after a pass.

Heater control. The heater is never switched on directly. Starting heater control is refused when the target is below 30 °C, cooling is active, the door does not read closed ("Door is Open - Operation Disabled") or the chamber thermistor is invalid; otherwise the heater fan is driven at 100 % (heater.fan_pwm), allowed 2 s to spin up and must reach 100 RPM (heater.min_fan_rpm) over 1 s, else heater control is refused. A PI controller with a delta-sigma modulator then switches the heater element every 50 ms to reach and hold the target; "at temperature" means within ± 1.5 °C. Every 10 s heater fan RPM and thermistor are re-checked; a failure, an invalid chamber reading at any sample, or an element state changed from outside switches the heater off at once and records a heater fault. UV LEDs are switched directly (no closed loop).

Heater fan during a run. From the start of a program until it ends, the heater fan is held at 100 % in every step — also in steps without heating — and a heater stop inside the run keeps it at that duty. On Pause and at the end of the run (completed, aborted or error) it is released into the normal run-on: heater element off at once, heater fan at 30 % (heating.cooldown_fan_pwm) for 15 min (heating.cooldown_sec = 900 s), then every fan off (fans of lit LEDs excepted) and the damper closed. A firmware stop or restart during heating, during a held run or during a run-on stores the run-on still due and resumes it on the next start. Only a door abort switches the heater fan off without run-on.

Temperature-sensor supervision (Err 9010–9014). Every NTC is read through a 10 kΩ pull-up divider; a disconnected sensor yields no temperature, and any reading outside −20…120 °C counts as not reading. A bad reading is first bridged by holding the last good value for up to 15 s (sensor_filter.glitch_hold_sec) — during that hold the heater controls on the held value — and only then counts as open. Each supervised sensor has its own code and its alert names only that sensor and clears by itself once it reads again:

  • Required sensors — chamber (TEMP_CHAMBER, 9010), Left LED (TEMP_LEFT_ORIGIN, 9011), Right LED (TEMP_RIGHT_ORIGIN, 9012), all critical. Open for at least one full minute → the alert is raised (checked every second from start-up). While a required sensor is open no step can start (step pre-flight, above). Heater sensor rule: the heater is never switched on while TEMP_CHAMBER does not read; when it stops reading while heating, the heater is switched off at once and 9010 is raised at once (not after the minute); on the Cure screen the run pauses (§7.3.6).
  • Diagnostic sensors — Back LED (TEMP_BACK_ORIGIN, 9013) and Door LED (TEMP_DOOR_ORIGIN, 9014): open for one minute → warning. Processes start and run as usual.
  • Frozen heater reading (Err 9006). While heating with the heater at ≥ 50 % output for 90 s continuously, TEMP_CHAMBER must move by at least 0.01 °C (frozen_reading); otherwise critical alert 9006, the heater element is switched off at once (the heater fan runs on), the alert names the reading and the value it is stuck at, and every heating start is refused with 9006. The machine restarts itself 60 s after the alert (reboot_after_sec), but not before the heater-fan run-on has finished; the latch is kept on disk and read back at start-up, so heating stays refused after the restart. A chamber holding its setpoint is not judged (output falls below 50 %). The latch clears once the reading moves by ≥ 1 °C or goes open (9010 takes over).
  • Heater not heating (Err 9007). While the heater control drives full output (≥ 99 %) for 600 s continuously and the chamber rose less than 0.5 °C above the lowest reading of that window (no_heat), critical alert 9007 "Heater Not Heating - Check Voltage Selector / Fuse"; the heater element is switched off at once (the heater fan runs on) and the alert names both causes (110 / 230 V selector not fully in position, blown heater fuse). The run ends error with 9007. The latch clears when heating is started again.
  • Other heater faults. A heater-control fault without its own code (e.g. heater fan below 100 RPM at the 10 s check) ends the run error with 6015 and "Heater stopped: <fault>". Chamber-sensor (9010) and frozen-reading (9006) faults do not end the run by themselves — the Cure screen pauses it and asks (§7.3.6).

Fan health supervision (Err 9020–9025 / 9060–9065). Every fan with a tachometer — heater fan, chamber cooling fan, the four LED fans — is compared once per second with its nominal RPM at the commanded duty (fan_health.nominal_rpm, linear interpolation between the measured points; heater fan 5,925 RPM at 100 %, chamber cooling fan 4,790 at 100 % / 2,690 at 60 % / 1,235 at 30 %, LED fans 3,560 at 100 % / 1,135 at 30 %; while the damper is open the chamber cooling fan is judged against nominal_rpm_damper_open, 4,075 at 100 % / 2,470 at 60 %). A reading counts only while the fan is commanded at ≥ 30 % and 5 s after a duty change; a condition must persist for one full minute:

  • ≥ 10 % below nominal for one minute → warning "replace the fan", one code per fan: 9060 heater, 9061 chamber cooling, 9062–9065 Left / Right / Back / Door LED fan. The machine keeps working.
  • ≥ 20 % below nominal (heater fan: ≥ 11.8 %, critical_below_pct_by_fan) for one minute, or ≤ 5 % of nominal (stopped) for 5 s → critical, one code per fan: 9020 heater, 9021 chamber cooling, 9022–9025 Left / Right / Back / Door LED fan. Every cure output is stopped at once, no step can start (refused with that fan's code) and the latch holds until the fan runs at nominal for a full minute again, the operator dismisses the fan alert on the Alerts screen (which acknowledges the fan alarm), or the fan is overridden (Continue anyway, §6.8 and §7.3.6).
  • The alert names the exact fan with measured and expected RPM, duty and deficit; the machine state publishes each fan's duty, measured and expected RPM, deficit and status (ok / warn / critical / pending / idle).

LED connection supervision (Err 9040–9043) — present but switched off in the shipped configuration (led_heating.enabled = false, decision 2026-09-16; the Cure-screen check of §7.3.6 follows the same switch; see OI-63). When enabled, the Left and Right panels are supervised through their regular thermistors (TEMP_LEFT / TEMP_RIGHT): while a panel is lit at ≥ 30 % system power, after 90 s of accumulated light it must have risen ≥ 1.0 °C above the baseline taken when it was lit (a panel re-lit within 120 s keeps its previous baseline), else critical 9040 / 9041 "LED Panel Not Heating - Check LED Connection"; once proven, a fall of ≥ 1.0 °C below its peak at the current power level (corrected for a falling chamber) lasting 30 s raises 9042 / 9043 "LED Panel Temperature Dropped During Cure" (120 s settle after a power change). The run is not aborted by these alerts; each clears by itself when its panel heats again (within 0.5 °C of its peak for a drop).

Door watchdog (Err 6016). Once per second: if the door reads open while any output is live (heater control, cooling, UV, N₂ valve, extraction or a fan group commanded by the controller) for door_sensor.abort_after_sec (10 s), the firmware performs the door abort (table above) and the running program ends error with 6016. Closing the door within the 10 s cancels it. An unreadable door sensor blocks heater and LED starts like an open door; the watchdog acts only on a door that reads open.

Output watchdog. The firmware writes a heartbeat once per second; a separate watchdog process checks it every 500 ms and, when it is older than 20 s, cuts the heater element, the four UV dimming channels and both UV supply SSRs, repeating the cut every 5 s while the silence lasts. Fans, damper and valves are left running so heat keeps being removed. A clean firmware shutdown removes the heartbeat and disarms the watchdog; on shutdown the firmware switches every output off.

7.6.1 Option 1 — Drying

The user sets the drying time, the target temperature (30–50 °C; the runner refuses a Drying step above 50 °C) and the Timer Start. The step pre-flight includes the chamber-fan spin test (9034). The damper is closed and the heater control heats to the target. The first time the heater control reports the target reached (within ± 1.5 °C) the damper opens and the chamber cooling fan runs at 30 % for the rest of the step, while the heater holds the target. The step ends when the ramp is complete (chamber ≥ target − 0.5 °C) and the step time has elapsed on its timer; the chamber fan and the damper are then set by the next step's command (Stop all after the last step).

7.6.2 Option 2 — Heating

The user sets the heating time, the target temperature (30–80 °C) and the Timer Start. After the pre-flight, UV is off, cooling and ventilation are stopped, the damper is closed and the heater control heats to the target and holds it. With Timer Start At temperature the step time is counted from the moment the chamber reaches target − 0.5 °C; with On ramp start it is counted from the step start, but the step never ends before the target is reached. When the time has elapsed the step ends; the heater keeps its fan at the run duty and the next step's command takes over (after the last step: Stop all, §7.4).

7.6.3 Option 3 — Curing / Bleaching

The user sets the process (Cure 405 nm or Bleaching 450 nm), time, target temperature (30–80 °C, or none), UV intensity (10–100 %), UV Start (On ramp start / At temperature), Timer Start (On ramp start / At temperature) and, for a step without a target, ventilation. Cure lights every panel allowed at 405 nm (Left, Right, Back, Door); Bleaching lights the panels allowed at 450 nm (Door only in the shipped configuration).

  • With a target. UV Start At temperature (default): the heater heats to the target with the UV off; when the chamber reaches target − 0.5 °C the UV is lit (a new step command with its own pre-flight and LED-fan spin test). UV Start On ramp start: heater and UV start together. The step time follows the Timer Start as in Heating. The target temperature and UV intensity are held until the time has elapsed.
  • Without a target (UV only). The heater element stays off (the heater fan keeps its run duty), the UV is lit at once and the step time starts immediately; with ventilation the damper opens and the chamber cooling fan runs at ventilation.fan_pwm (60 %).
  • No LED self-test at the step start. Before UV is lit only the LED-fan spin test runs (9030–9033). The lit-panel heating checks (9040–9045) exist but are switched off in the shipped configuration (§7.4, §7.3.6). A lit-panel LED test runs only in the power-on self-test.

7.6.4 Option 4 — Cooling

The user sets the target temperature and the cooling mode (Fast / Medium / Slow). After the pre-flight (with the chamber-fan spin test, 9034) the UV and the heater are switched off, the damper opens, the heater fan runs at 100 % and the chamber cooling fan at a fixed duty for the whole step — Fast 100 %, Medium 60 %, Slow 30 % — with Fast also running the four LED fans at 100 % while no LED is lit. There is no closed-loop control of the cooling rate; the rate is measured for status only (OI-44). The step ends when the chamber is at or below target + 0.5 °C; the cooling control itself stops at the target (fans off, damper closed) if the next step has not taken over first.

7.6.5 Option 5 — N₂ Purge

An N₂ Purge step runs only when Nitrogen Mode is on (Settings, §11); otherwise it is dropped from the run, and a program consisting only of N₂ steps cannot be started (§6.8). The step opens the N₂ valve for a fixed 120 s and then closes it; no other output is touched and no pre-flight, line-pressure or availability check runs at the step (OI-43). The program rules (§6.7.2) require the purge to be followed by a Cure or Bleaching step and that by a Cooling step, which vents the nitrogen through the open damper; at most two purges per program.

8. Cure History Screen

8.1 Purpose

The Cure History screen is the log of the cure runs recorded on the device. It is opened from the History icon in the top bar. It lists the past runs (and a run in progress) with their outcome, timing, step progress and the sensor or fan problems seen during the run. A detail panel shows the selected run. From the panel the operator exports the run's cure report to a USB drive and deletes one run or the whole history. 9. Error Management, Alerts Screen & Registry

Every error and warning surfaced anywhere in the system is defined once, in a single central Error Registry. A condition is raised by its stable numeric code, and the text the operator sees (message, description, troubleshooting, support and video links) is resolved from the registry by that code. Source of truth: sCureBox-CS/config/errors.json (registry _meta.version 4.0.0, 76 records, sCure CS firmware 1.0.106). The firmware reads the registry once when the application starts; if the file is missing or unreadable, a built-in minimal registry is used (§9.8).

9.1 Principles

  • One registry, one definition per error. Each error appears exactly once in the registry. Requirement ERR-01 applies to every error state; screens that still show their own text for a registry-listed condition are listed in §9.11 (OI-59).
  • Stable, unique number. Every record has a permanent numeric code that never changes once assigned and is never reused.
  • One code per component. Since firmware 1.0.106 every thermistor, fan and LED panel that can fail has its own code, so each has its own title, troubleshooting steps and repair video. The earlier grouped codes (9001–9005, 9050, 9051) are no longer raised; they remain in the registry as the family of their per-component codes, so older cure reports and logs still resolve to a title, and any rule that reacts to a kind of fault (e.g. "any fan-stop code") matches the whole family (§9.11.6).
  • Uniform record. Every record has the same shape — code, key, message, severity, category, layer, plus support content (§9.2).
  • Editable message. Support / CS may edit message and the support content; the operator-facing text changes without any code change (§9.9).
  • Numbering by SRS section. The first digit of the code identifies the SRS section / screen the error is documented in (§9.3).
  • Code carried unchanged. A code raised by the machine travels unchanged to the screen, the cure report and sCure Cloud; nothing re-words or re-maps it (§9.4).

9.4 Layer Tagging & Code Propagation

The number encodes the section; the originating subsystem is recorded separately in the layer field. The number is the contract everywhere:

  • Machine refusals. A command the machine refuses (a process step, a heater command, a UV start) returns { ok:false, code, message }. A refusal that carries its own code (e.g. 9010, 9020–9025, 9030–9034, 9006) keeps it; a refusal without one is reported as 6015 Pre-Cure Check Failed. Request validation returns 7001 / 7002 / 7003. Source: sCureBox-CS/src/SCureBox.Api/Infrastructure/ApiJson.cs, src/SCureBox.Domain/Errors/ErrorCodes.cs.
  • Machine alert list. The machine state carries the list of currently active supervision codes together with one detail line per code naming the exact component and the measured value (e.g. "Heater fan (FAN_HEATER): 4,900 RPM measured, 5,925 RPM expected …"). The screen mirrors this list (§9.6).
  • Service operations. Network diagnostics, USB export, log export and software update return their own 908x code with the message (§9.11.6).
  • No consumer re-words or re-maps a code: the screen, the cure report (§9.6.3) and sCure Cloud all show the code as raised and resolve its text from the registry.

9.6 Error Lifecycle

An error definition (registry record) is static; an active alert is a runtime instance of one. An alert exists at two levels: the machine alert list (the live condition) and the screen's active set (what the operator sees and dismisses).

9.6.1 Machine level

  1. Detect — the supervision runs once per second (§9.14); start / step pre-flight checks and the door watchdog run on their own triggers.
  2. Raise — the code enters the machine alert list with a detail line naming the component.
  3. Clear — most codes clear by themselves as soon as the condition clears (sensor reads again, fan back at nominal speed, panel heats again). Latched codes follow their release rule: fan-stop codes (60 s running at nominal speed, or an operator acknowledge while the fan is not failing), 9006 (reading moves by 1 °C or more, or the sensor reads open), 9007 (the next heating start), 6016 (acknowledge or the next process start).

9.6.2 Screen level (Alerts screen)

  1. Raise — every code in the machine alert list is raised on the screen with its detail; codes are also raised directly by a screen when an operation it ran is refused or fails (e.g. a cure-start refusal, a USB export, enabling NFC). A new alert gets a unique instance id, the code, a timestamp, the detail and dismissed:false.
  2. De-duplicate — raising a code that is already active (undismissed) creates no second alert; only its detail line is refreshed when it changed.
  3. Surface — the top-bar bell shows the active count and the highest active severity; the Alerts screen lists the alert; the critical / warning counts are reported to the machine's status strip (§9.6.3).
  4. Inspect — the operator opens the alert detail (§9.7.3).
  5. Dismiss — the operator dismisses one alert at a time (there is no "clear all" control on the screen). Dismissing 6016 acknowledges the door abort on the machine; dismissing any fan code (9020–9025, 9030–9034, 9060–9065, or the grouped 9002 / 9003 / 9051) acknowledges the fan alarms on the machine (§9.14.2). The machine records each fan-alarm acknowledge, with its time and what it released, in the system log.
  6. No re-raise of a deleted alarm — a machine code the operator dismissed while the machine still lists it is not raised again until the machine drops the code or its detail changes (e.g. another fan).
  7. No auto-clear on the screen — an alert stays in the screen's active set until the operator dismisses it, also after the machine has cleared the condition (OI-61).

9.6.3 Records & reporting

  • Cure report. Every code that appears in the machine alert list while a program runs is recorded in the run with its time since start and detail (a code that clears and comes back is recorded again), plus the code that ended a failed run. Source: src/SCureBox.Application/Recipe/RecipeRunner.cs.
  • sCure Cloud. The machine samples its alert list every second and keeps an alert log of the last 48 hours (code, detail, raised and cleared time; at most 300 entries), uploaded with each cloud sync for the portal's "Errors today" view. Source: src/SCureBox.Application/Platform/CloudSyncAgent.cs.
  • Status strip. The screen reports its critical and warning counts to the machine on every change and every 30 s; a report is honoured for 90 s. A critical count drives the strip to its fault state, a warning count to its warning state (status strip priority: §7 / §11).

9.8 Persistence, Deduplication & Fallback

  • Persistence. The screen's alerts (active and dismissed) are stored on the device in data/ui-alerts.json and survive an application restart or reboot.
  • Load filter. On load, any stored alert whose code is no longer in the registry is dropped, so a stale entry can never leave the bell counting unresolvable alerts. An undismissed 9052 (NFC reader) is also dropped — it is a live condition that the machine raises again if it still applies.
  • Deduplication. Raising a code that is already active adds no duplicate (§9.6.2).
  • Registry load & fallback. The registry is read from config/errors.json when the application starts. If the file is missing or malformed, a built-in minimal registry is used; it covers only the codes the firmware itself raises, with short messages and no troubleshooting, and differs from errors.json in some keys, messages and severities (OI-60). Source: src/SCureBox.Domain/Errors/ErrorRegistry.cs.
  • No demo data. The screen shows only real alerts; no demonstration alerts are seeded.

9.9 Registry Governance & Editability

The registry _meta carries a version and lastUpdated, and declares editableFields vs systemFields so tooling can enforce that CS only changes the editable fields.

  • CS / support may edit message, description, troubleshooting, supportUrl; the service team sets videoUrl with the registry editor.
  • Engineering owns code, key, severity, category, layer and allocates new codes.
  • When an edit takes effect. The machine reads the registry at application start, so an edited registry is shown after the next start of the application. How an edited registry reaches installed machines is not yet defined (OI-62).
  • Adding an error: allocate the next free number in the range of the SRS section it belongs to (for a component fault, in its family's per-component sub-range, §9.3); never reuse or renumber an existing code; add the record to the registry, the catalog (§9.11) and the relevant diagram node (§9.12).

9.13 Numbering History

The registry has gone through three numbering changes; in each, the key of a surviving error (e.g. USB_WRITE_FAILED) stayed constant, so traceability is preserved.

  • v1 → v2. Severity-prefixed codes (E-1xx critical, W-3xx warning) were replaced by numeric codes; severity became an explicit field.
  • v2 → v3. The first digit was re-based from subsystem (1=daemon, 2=backend, 3=UI) to SRS section (3=Setup … 9=Error Management). The subsystem information is held in the per-record layer field.
  • v3 → v4 (registry 4.0.0, firmware 1.0.106). One code per component: the grouped hardware codes 9001–9005, 9050 and 9051 were split into per-thermistor, per-fan and per-panel codes (9010–9014, 9020–9025, 9030–9034, 9040–9045, 9060–9065). The grouped codes were kept as family titles, not deleted or reused.

Intermediate v2 numbers were never shipped and are not preserved.

9.14 Hardware Supervision — Alert Sources

Detection rules, consequences and clear rules of the device alerts in §9.11.6, as implemented in firmware 1.0.106. Thresholds are configuration values in sCureBox-CS/config/components.json (sections fan_health, frozen_reading, no_heat, led_heating, door_sensor); the values stated are the shipped ones. The supervision runs once per second. Source: src/SCureBox.Application/Supervision/, src/SCureBox.Domain/Control/.

9.14.1 Temperature sensors (9010–9014)

  • A supervised thermistor is open when it gives no reading or a reading outside −20…120 °C.
  • An open thermistor raises its own code after 60 s of continuous open reading. Required sensors (critical): chamber 9010, Left LED 9011, Right LED 9012. Diagnostic sensors (warning): Back LED 9013, Door LED 9014 — processes keep running.
  • The chamber thermistor is the heater's own sensor: if it stops reading while heating is active or wanted, 9010 is raised at once (no 60 s wait) and the heater is switched off at once. A heating command is refused while it does not read.
  • Before every process step the required sensors are read up to three times 0.5 s apart; if any stays open the step is refused and each open sensor's code is raised at once (§9.5.1).
  • Each code clears by itself as soon as its sensor reads again.

9.14.2 Fan health (9020–9025 stop, 9060–9065 wear)

  • Each fan with a tachometer is judged while it is commanded at 30 % duty or more, after a 5 s settle following a duty change, against its nominal RPM at the commanded duty (interpolated from the nominal_rpm table; the chamber cooling fan uses its damper-open table while the damper is open).
  • Wear (warning). 10 % or more below nominal for 60 s → the fan's wear code (9060–9065). Nothing stops; the code clears when the fan is back within 10 %.
  • Stop (critical). 20 % or more below nominal (heater fan: 11.8 %) for 60 s → the fan's stop code (9020–9025); a fan reading 5 % of nominal or less trips after 5 s. Every output is switched off at once.
  • Latch. A stop code is latched and blocks every process start until it is released: by 60 s of running at nominal speed, or by an operator acknowledge (dismissing a fan code on the Alerts screen) while the fan is not measured failing at that moment. A fan that is still driven and failing keeps its latch.
  • Override. When the Cure screen offers to continue without a failed fan and the operator accepts, that fan is overridden: it keeps being reported but no longer stops outputs or blocks starts; overrides are cleared when the run ends (§7).
  • The alert detail names the fan with measured and expected RPM, duty, deficit and duration.

9.14.3 Fan spin tests before a step (9030–9034)

  • LED fans (9030–9033). Before UV LEDs are switched on, the cooling fans of the panels about to be lit are driven at 100 %, given 1.5 s to spin up and measured over 0.5 s. A fan below 100 RPM (or unreadable) raises its own code; the fans are switched off, the UV is not switched on and the step is refused. The test is skipped while UV is already on, for 30 s after a passing test, and for overridden fans.
  • Chamber cooling fan (9034). The same test runs before a drying or cooling step (the steps that use this fan); heating and UV steps do not test it. It is skipped while cooling already drives the fan, for 30 s after a passing test, and when the fan is overridden.
  • A code clears when the next test of that fan passes, or on an operator acknowledge / override.

9.14.4 Heater supervision (9006, 9007)

  • 9006 Temperature reading frozen. While heating with the heater at 50 % output or more continuously for 90 s, the chamber reading must move by at least 0.01 °C; otherwise 9006 is raised, the heater element is switched off at once (the heater fan runs on), every heating command and every process step is refused, and the alert names the frozen value. The machine restarts itself 60 s after the alert, waiting for the heater-fan run-on to finish first; the latch is kept on disk, so heating stays refused after the restart. 9006 clears when the reading moves by 1 °C or more from the frozen value, or the sensor reads open (then 9010 applies). A drop of the output below 50 % (holding near the target) restarts the window.
  • 9007 Heater not heating. While the heater is driven at 99 % output or more continuously for 10 minutes, the chamber must rise at least 0.5 °C above the lowest reading of that window; otherwise 9007 is raised and the heater element is switched off (the heater fan runs on). The alert names both likely causes (110 / 230 V selector not in position, blown heater fuse). A program run ends with status error. 9007 clears at the next heating start, which judges the heater afresh; it does not block a start.

9.14.5 LED panel checks (9040–9045)

The LED checks are switched off in the shipped configuration (led_heating.enabled = false): no 9040–9045 is raised by the machine or by the Cure screen (OI-63). When enabled:

  • Machine check (Left / Right). After 90 s of light at 30 % system power or more, the panel thermistor must have risen at least 1.0 °C above its temperature when the light started (9040 / 9041). A panel that had warmed and then falls 1.0 °C or more below its peak at that power (after subtracting any chamber fall) for 30 s raises 9042 / 9043; a power change gets 120 s to settle. The process keeps running; each code clears when the panel heats again (within 0.5 °C of its peak for 9042 / 9043).
  • Cure-screen check (all four panels). When UV turns on, every panel below 30 °C is noted (the Door panel is skipped while bleaching); after 15 s (30 s below 60 % intensity or while bleaching) each must have risen by max(0.35, 0.8 × intensity/100 × window/15) °C. Each cold panel raises its own code (9040, 9041, 9044, 9045) and the screen offers continue (the panel is not judged again this run) or stop (§7).

9.14.6 Door watchdog (6016)

  • If the door is open while any output is live (heater, cooling, UV, N₂, BOFA or a manual fan duty) for 10 s (door_sensor.abort_after_sec), the process is aborted, every output is switched off and 6016 is raised and latched (status strip in fault state). Closing the door within the 10 s lets the process continue.
  • The latch is released by dismissing 6016 on the Alerts screen (acknowledge) or by the start of the next process.

9.14.7 Other sources

  • 9052 NFC reader. Raised when NFC is switched on with no reader detected (the switch stays off), and when a reader that had been detected since boot is disconnected while NFC is enabled. A machine that boots without a reader raises nothing.
  • 9089 machine state unreadable. Raised on the screen when it can no longer read the machine state (once per loss).
  • 908x service faults. Network diagnostics (9080, 9084, 9085), USB / log export (9081, 9082, 9083) and software update (9081, 9086, 9087) are raised by the screen that ran the operation.
  • Output watchdog. A separate supervisor process switches the heaters and UV LEDs off when the firmware's heartbeat has been silent for 20 s, and again every 5 s while it stays silent. It writes to the system log only and raises no registry code (OI-64).

10. Data Architecture & Persistence

All application data of an sCure unit — released materials and user programs, print history, cure runs with their telemetry, the generated cure reports, the measured phase timings, settings, alerts and component counters — is stored on the unit itself, in its data directory. By default every record is kept in JSON files written atomically; a PostgreSQL database is an optional alternative backend for materials, print history and cure runs only, used when one is configured and reachable at start-up (§10.1). The shipped unit configuration does not configure a database, so a unit in the field runs on the JSON files. Configuration (error registry §9, presets, system identity, release history) is read-only and shipped with the software; the machine's hardware map is the unit's own and is kept across updates (§10.4). A data subset is sent outbound to sCure Cloud when cloud sync is configured (§10.6).

10.1 Storage Backends & Selection

  • Data directory. Every data file lives in one directory: /var/lib/scurebox on a unit installed from the sCure image or installer, /opt/data/scurebox/data when sCure runs as an Origin application package. The directory is outside the application folder, so a software update never replaces it. Source: deploy/scurebox-ui.service, deploy/origin-app/run.sh, deploy/install.sh.
  • Default backend — JSON files. Used whenever no database connection is configured, or the configured database cannot be opened or initialized at start-up.
  • Optional backend — PostgreSQL. Used only when a connection string is configured (DATABASE_URL) and the database answers and accepts the schema at start-up. It then replaces the JSON stores for materials / user programs, print history and cure runs (with telemetry and reports). All other data (phase timings, settings, alerts, counters, calibration, cloud state, safety markers) always stays in the JSON files.
  • Sticky decision. The backend is chosen once per start of the firmware and is not re-evaluated while it runs. A database that fails at start-up is not retried until the next start; the unit runs on the JSON files meanwhile. Data written to one backend is not copied or migrated to the other (OI-65).
  • No data unavailability state. Because the JSON backend is always available, the data screens never show a "database unavailable" condition; there is no 503 path. Source: src/SCureBox.Application/Persistence/StoreSelector.cs.

10.3 Cure-Run Record Lifecycle

  1. Start. When a program starts, a run record is created with status running: run id, material name, number of steps, phase list, first target temperature, unit serial number and start time. If 25 runs already exist, the oldest beyond 25 are removed with their telemetry and reports.
  2. Telemetry. A telemetry sample is recorded every 2 s while the run is active. In the JSON backend the history file is rewritten every 15 samples (about 30 s), so the storage is not rewritten every second.
  3. Phase timing. At the end of every phase its real timing is appended to the phase-timing record (§10.2).
  4. Finish. On completion, abort or error the record is closed immediately with the final status, end time, duration, steps completed, the sensors that read open-circuit during the run (sensorIssues), the fans that ran below nominal (fanIssues) and the alerts raised during the run.
  5. Report. When the cure completes the report is generated from the run's telemetry, stored with the run and exported to the USB drive (§8). A run without telemetry gets no report.
  6. Interrupted run. A run still marked running when the firmware starts (power cut, crash) can never finish; the JSON backend rewrites it to error at start-up so the history never shows a run that cannot end.
  7. Deletion. A finished run, or all finished runs, can be deleted from Cure History (§8); the run's telemetry and report go with it, and the same run ids are queued for deletion on sCure Cloud. A run in progress is never deleted.

10.5 Power Loss, Update and Reflash

  • Power loss. Every data file is written whole, through a temporary file and a rename, so a power cut never leaves a half-written file. A missing or unreadable file is treated as empty (the unit starts with an empty list / defaults and keeps running) and is not repaired. The expected losses are listed in §10.2.
  • Software update / re-install. The data directory and the unit's components.json are kept; the application and its config folder are replaced.
  • Reflash of the eMMC image. Writing a new image replaces the whole storage, so all data on the unit is lost (programs, cure history, reports, counters, calibration, settings). The unit offers no backup or export of its data before a reflash; only what was sent to sCure Cloud (§10.6) and reports exported to USB remain (OI-67).

10.6 Cloud Sync of Data

Cloud sync is off until it is configured (portal URL + machine key). When on, the unit connects outbound only at the configured interval (minimum 3 s, default 10 s). Source: src/SCureBox.Application/Platform/CloudSyncAgent.cs, CloudReportDeletions.cs.

  • Sent each sync: machine state (temperatures, door, heating / cooling / UV, internet) with the component counters; the user programs; the last 20 print-history entries; the last 10 cure runs without telemetry; the alerts of the last 48 h (at most 300 entries); and the ids of the commands applied since the previous sync.
  • Reports: when the portal declares that it keeps reports, one report per sync is uploaded — the newest finished run of the last 10 the portal does not have yet (the stored report, or one built from the run's telemetry). Each report is uploaded once.
  • Deletions: runs deleted on the unit are queued and the portal is asked to delete their reports; a deletion made offline is sent on the first sync that succeeds.
  • Commands received are data only — create / replace a user program, delete a user program, add a print-history entry. No command actuates hardware. Each command is applied once (acknowledged on the next sync).
  • Cloud sync is not a backup: the cloud receives summaries and reports, not the complete history or telemetry, and the unit never restores data from the cloud.

11. Settings Screen

11.1 Purpose

The Settings screen is the device's control and maintenance panel. From it the operator sets the System Name, reboots the device or puts it to sleep, works the hardware directly (damper, fan groups, chamber heating), runs the fan and LED diagnostics, reads the component wear counters and the N₂ line pressure, switches Nitrogen Mode, NFC and BOFA, sets the clock, exports the logs, updates the software, views compliance, links or changes the organization, and views the software version. It is also one of the two entry points to Developer Mode. It is opened from the gear icon in the top bar. The icon does nothing while the Cure Process screen is open. Source: sCureBox-CS/src/SCureBox.Ui/ViewModels/Pages/SettingsViewModel.cs, src/SCureBox.Ui/ViewModels/Settings/FanRowViewModel.cs, src/SCureBox.Ui/Views/Pages/SettingsView.axaml.

11.5 Developer Mode

  • Entry. Developer Mode is opened in either of two ways: the tenth press of the top-bar gear (the press count is kept for the session, and that press opens the PIN pad instead of Settings), or ten taps on the Versions card. Both are ignored while already in Developer Mode.
  • PIN. A four-digit PIN pad. A correct PIN enters Developer Mode and opens the Developer Tools menu. A wrong PIN shows "Incorrect password" and clears the entry. Request, success, failure and exit are written to the developer event log. The PIN is one fixed value in the firmware, the same on every unit (OI-57).
  • Scope. Developer Mode lasts for the session only: it ends on Exit Developer Mode or a restart. While it is on, the top bar shows a DEV badge that opens the Developer Tools menu: LED Intensity Calibration and Material HDT Calibration. Opening a developer screen outside Developer Mode returns to Home. These developer screens are not specified in this document (OI-58).

11.7 Error Handling & Edge Cases

  • Reboot. REBOOT asks for confirmation. A refused reboot is reported on the Restarting screen.
  • No USB drive. Export Logs shows "✗ No USB drive found" and raises Err 9083. The Software Update modal stops at the USB or package step with the reason.
  • Nitrogen guard. Nitrogen Mode cannot be switched on while the N₂ line pressure reads below 1 bar (§7).
  • NFC guard. NFC cannot be switched on without a detected reader (Err 9052).
  • Heating refused. The returned code is raised as an alert and the slider returns to OFF. A sensor-not-reading (9010 family) or frozen-reading (9006) refusal also opens an explanation dialog.
  • Diagnostics time-outs. Fan test: FAIL after 20 s without an answer. LED test: "no answer" after 120 s. The LED test is refused while a process is active.
  • Organization CSV. A file with no valid UUID shows "No valid ID found" and does not change the organization (cf. §5, registry 5001).
  • Invalid manual date. A date that does not exist is rejected with "✗ Failed".
  • During a cure. The gear icon (and the other top-bar navigation) does nothing while the Cure Process screen is open (§7).

(c) Confirm the acceptance values: door wait 60 s, sensor wait 5 s, LED tests 15 s (405 nm) / 30 s (450 nm) with a 0.8 °C panel rise, and skipping the LED and fan checks after a planned restart within 10 minutes. (§3.3.1)
OI-34 — Origin sign-in methods on the unit. On the unit the Origin website is shown inside the sign-in dialog by a browser without its own window (the configuration's "auto" mode). The firmware's own configuration notes that Google sign-in refuses this mode; sign-in with Google / Microsoft works only when the browser has its own window. Questions: (a) Which Origin sign-in methods (e-mail / password, Google, Microsoft) must work on the unit? (b) Should the step check the internet connection before opening the website and show a specific message when it is offline? (§5.3.3)

§6 Home

OI-35 — Bundled presets vs. the program rules. The six presets shipped with CS 1.0.106 (config/presets.json / deploy/db/seed_presets.sql) do not all satisfy the rules the editor and the CSV import enforce: every preset has Cooling targets of 25 °C (editor / import window 30–75 °C; the machine accepts 20–80 °C at Start), and ABS-Like has an N₂ purge followed by a Heating step (the rules require N₂ → Cure/Bleaching → Cooling). Consequences: ABS-Like is refused at Start when Nitrogen Mode is on, and a duplicate of a preset cannot be saved unchanged (ABS-Like) or is silently changed by the editor's clamping (Cooling raised to 30 °C). Question for the owner: should the presets be corrected to the rules, or should the rules (Cooling minimum, N₂ block) be relaxed? (§6.5, §6.7.2)
OI-36 — Edit / Delete on preset rows. In edit mode the Edit and Delete buttons are present on preset rows with their icons hidden. Delete ignores presets, but tapping the hidden Edit position opens the editor on the preset, and Update Program would store a user program carrying the preset's id. Question for the owner: confirm that presets must offer no Edit action at all (button absent), and what should happen to a program already saved this way. (§6.6.2, §6.7.5)
OI-37 — Print ids kept after a View All pick. A plain row pick in Print History hands the print id back to Home; it is kept until Home is left, even if the operator then selects a different program, and the print is removed from the history when the next cure completes — whatever program ran. Cure Together with one selected print only selects the program, while two or more start the cure at once. Questions for the owner: should the pending print ids be cleared when the operator changes the selection, and should Cure Together with a single print also start the cure? (§6.4.1)
OI-38 — Unit of the print duration. Home and Print History treat duration as seconds (shown as minutes, rounded up) and the database derives the print end time from it in seconds, but the cloud portal's send_print command falls back to the program estimate in minutes (or 20) when no duration is sent. Question for the owner: confirm that duration is seconds in the portal contract and that the fallback must be converted. (§6.4)
OI-39 — Program names are not unique. The editor and the CSV import accept a name that another program already has, while a recent print or a Print History entry resolves its program by name (first match in the list order, favorites first) — so favoriting can change which program a print runs. Question for the owner: must program names be unique (and if so, how is a clash on Save / import reported), or should prints reference the program by id? (§6.4, §6.5)
OI-40 — N₂ time in the Home estimate. The Program List and the editor always count 120 s per N₂ purge, while the Cure Process screen leaves the N₂ steps out when Nitrogen Mode is off, so the two estimates differ for programs with N₂ steps. The 120 s is a fixed value, not read from the configuration. Question for the owner: should the Home estimate follow Nitrogen Mode, and what is the real purge duration to use? (§6.7.3)
OI-41 — Blank Cooling temperature in a CSV. The CSV parser turns a blank Cooling temperature into 25 °C, which the program rules then always reject (Cooling 30–75 °C), so the file fails with a message about a value the user never wrote. Question for the owner: should a blank Cooling target default to a valid value (e.g. 30 °C), or be reported as "Cooling needs a target temperature"? (§6.7.4)

§7 Cure Process

OI-42 — Door opened during a run: "Process Paused" is shown, but the run is not paused. When the door reads open mid-run the Cure screen shows "Door Open — Process Paused" with a 10 s countdown, but sCure CS 1.0.106 does not pause the run: heater control and lit UV stay commanded, the step timer keeps counting, and only the door watchdog aborts after 10 s (6016). The software refuses only new LED / heater starts while the door is open; whether the interlock relays K1 / K2 cut the LED supply in hardware when the door opens cannot be confirmed from the code. Question: should a door opening mid-run immediately switch off UV and heater and freeze the step clocks (a true pause) for the 10 s grace, or is the current wording to be changed to match the behavior? (§7.3.6, §7.4)
OI-43 — N₂ Purge step: no availability check, fixed duration. In sCure CS 1.0.106 an N₂ Purge step only opens the valve for a fixed 120 s: no step pre-flight (sensors, critical fan), no N₂ line-pressure / availability check at the step (the only gate is that Nitrogen Mode can be switched on in Settings from 1 bar), and the duration is not configurable. The previous SRS required "verify the N₂ system is available and connected, else error, the process does not start" and a "preset" fill duration. Questions: (a) must the purge step check the line pressure (which threshold, which error code) and run the step pre-flight? (b) is 120 s the required fill time, or should it be a system setting? (§7.4, §7.6.5)
OI-44 — Cooling modes are fixed fan duties, not controlled rates. sCure CS drives the chamber cooling fan at a fixed duty per mode (Fast 100 % / Medium 60 % / Slow 30 %, Fast also the LED fans) for the whole step; the cooling rate is only measured for status. The previous SRS required the system to "monitor the chamber temperature and modulate the cooling to the selected rate". Question: is the fixed-duty behavior the requirement, or is a closed-loop cooling rate (with target °C/min per mode) required? (§7.6.4)
OI-45 — Actuator timing figure no longer matches the firmware. The inline timing figure of §7.7 shows Drying → Heating → Cure → Cooling → N₂ with N₂ as the final phase, which the program rules reject (N₂ must be followed by Cure / Bleaching and then Cooling); it also shows the damper / air-in fan raised for the whole Drying phase (CS: only from the target) and a steady heater-fan level (CS: 100 % for the run, 30 % run-on after). The signal list under the figure has been updated as the normative text. Question: which representative program should the figure show (e.g. Heating → N₂ → Cure → Cooling), so it can be regenerated with tools/gen-timing.mjs? (§7.7)
OI-46 — Abort: no error code and no immediate cut. An operator abort in sCure CS ends the run with status aborted and no code — Err 7005 "Cure aborted" exists in the registry but is never raised — and the "immediate" stop is identical to a normal stop (the heater fan still gets its 15 min run-on; only a door abort cuts the heater fan at once). Questions: (a) should an operator abort record / raise 7005 in the run and on the Alerts screen? (b) is the run-on after an abort the intended behavior? (§7.3.5)
OI-47 — Run supervision lives in the Cure screen only. The temperature-stall warning (7004), the pause on a lost chamber sensor (9010) or frozen reading (9006), the pause with Continue anyway on a fan failure, and the LED-panel check are performed by the Cure Process screen, not by the firmware run. A run started over the HTTP API (/api/recipe/start) gets none of them — e.g. after a critical fan stops every output, that run stays running with its outputs off and waits for a target it cannot reach. Also, the Temperature Warning does not pause the run while it waits for the operator. Questions: (a) must these reactions be enforced by the firmware for every run, whoever started it? (b) should the Temperature Warning pause the run until Continue / Abort? (§7.3.1, §7.3.6)
OI-48 — Sensor / fan issues of a run are taken only at its end. For a run executed by the firmware (the Cure screen path), the run's sensor issues and fan issues are the sensors not reading and the fans in warning / critical at the moment the run finishes; a sensor that was open mid-run and read again before the end is not listed there (it does appear in the run's "alerts during the run"). The data model (§10, cure_runs.sensor_issues) describes them as "open at any point of the run", which only the older HTTP cure-run path does. Question: should the run record accumulate sensor and fan issues over the whole run? (§7.3.8)

§8 Cure History & §11 Settings

OI-49 — Cure report file name and export failures. (a) A report exported from Cure History gets a different file name depending on whether it was already saved: cure-report-<Material>-<yyyy-MM-dd>.html for a saved report, scure-report-<Material>-<yyyyMMdd-HHmm>.html for a newly built one. Two runs of the same Material on the same day overwrite each other under the first pattern. (b) The report export failures 9081 / 9082 appear only as a 3 s message and are not raised on the Alerts screen, while a log-export failure raises 9083. Questions: which single file-name pattern is required, and must it be unique per run? Must report-export failures be raised as alerts? (§8.3.2)
OI-50 — Operator feedback when a Settings command is refused or fails. In sCure CS 1.0.106 several Settings commands fail silently or with a generic result. A refused damper or BOFA command is only logged. A fan-speed change refused because the heating loop, the cooling loop or fast cooling owns the fan is not shown, and the slider keeps the refused value. An LED test that cannot run (process active, door open, invalid panel sensor, LED-fan pre-flight failed) shows only "FAIL" without the reason. A heating refusal other than a sensor fault raises the generic code 6015 ("Pre-Cure Check Failed"). Export Logs shows "No USB drive found" for every failure, including a copy failure on a USB drive that is present. Question: which of these must show a message or raise a specific registry code, and with what text? (§11.3)
OI-51 — Fan sliders: start value and lifetime of a manual duty. The three fan sliders start at 0 % on every visit instead of showing the fans' actual duty. A duty set from Settings is not reset when the screen is left, so a manually started fan keeps running until another command changes it. Questions: should the sliders show the current duty? Should a manual fan duty be cleared when Settings is left, after a timeout, or at the next process start? (§11.3)
OI-52 — Fan test shows a nominal RPM for a stopped fan. When the fan test measures 0 RPM, the result row shows a fixed nominal value (2850 / 3050 / 2780 RPM for LED cooling / chamber intake / chamber heating) next to FAIL instead of the measured 0. The failure line below gives the real reading. Question: confirm that the row must show the measured value (0 RPM), and whether the fixed nominal values are still needed anywhere. (§11.3)
OI-53 — Nitrogen Mode pressure limit. sCure CS lowered the Nitrogen Mode limit from 6 bar to 1 bar (owner decision of 2026-10-18 recorded in the code), and the N₂ Pressure field now shows the live line-pressure reading. The limit is checked only when a reading exists: with no reading ("N/A", for example no sensor or sensor fault) Nitrogen Mode can be switched on. Nitrogen Mode is also not switched off when the pressure later falls below the limit. Questions: confirm the 1 bar limit; must Nitrogen Mode be blocked without a pressure reading; must a pressure drop below the limit while Nitrogen Mode is on turn it off or raise an alert? Supersedes OI-27. (§11.3)
OI-54 — Auto Sync and network time. Manual Apply now sets the operating system clock, and in doing so turns network time synchronization off. The Auto Sync switch only changes the view: it is not saved (it is on again at every visit) and turning it on does not turn network time back on. After one manual change the device therefore never resynchronizes, although the screen shows Auto Sync on. The time zone cannot be changed. Questions: must Auto Sync be a stored setting that turns network time on and off? Who may set the clock manually? Is a time-zone setting required? Supersedes OI-28. (§11.3)
OI-55 — Unlink without confirmation. Unlink clears the organization, marks Setup as not complete, and sends the device straight back to the Setup screen. There is no confirmation and no PIN, and it is reachable by any operator outside a cure. Question: should Unlink ask for confirmation (or a PIN), and should it return to Setup or only clear the organization? (§11.3)
OI-56 — UV lead on-time and maintenance warning. Earlier revisions showed a Lead On Time value on Settings that drove a maintenance warning (W/1053). sCure CS shows component on-hours (LED 405 nm, LED 450 nm, cooling fan, heater, heater fan) but has no Lead On Time field, no maintenance threshold and no 1053 code. Question: is a maintenance warning based on component on-hours required? If so, for which components and at which hour limits, and with which registry code? (§11.3)
OI-57 — Developer Mode PIN. Developer Mode is protected by one four-digit PIN fixed in the firmware and identical on every unit. There is no attempt limit or lock-out, and failed attempts are only written to the developer event log. Question: is a shared fixed PIN acceptable for CRA / EN 18031, or is a per-unit or service-account credential with an attempt limit required? (§11.5)
OI-58 — Screens not specified in the SRS. sCure CS has screens that no SRS section specifies: the Network screen (top-bar globe icon: status, diagnostics, DHCP / static IP) and the Developer Mode screens LED Intensity Calibration and Material HDT Calibration, as well as the full-screen Restarting screen used by Reboot and Software Update. Question: should these get their own SRS sections, and who owns them? (§11.3, §11.5)

§9 Error Management

OI-59 — Registry codes that CS 1.0.106 does not raise. The registry defines 3001–3003, 4001–4003, 5001, 6001–6014, 7005 and 9088, but firmware 1.0.106 never raises them: the matching screens (setup, name, organization, program editor, CSV import, Cure Together, nitrogen-only start, update) show their own inline text, and an update integrity failure is reported as 9086. This conflicts with ERR-01 and leaves the §9.12 diagram codes untraceable on the machine. Question: should these screens raise their registry codes (as Alerts entries, or as inline text resolved from the registry by code), or should the unused codes be retired from the registry and the diagrams? (§9.1, §9.11, §9.12)
OI-60 — Built-in fallback registry differs from errors.json. When config/errors.json is missing or malformed the firmware uses a built-in registry that covers only the codes it raises and differs from the file: 7004 is critical (file: warning), 9004 / 9005 are warnings (file: critical), 6016 has key DOOR_OPENED_DURING_CURE (file: DOOR_OPENED_MID_PROCESS), several keys / messages / categories differ (e.g. NO_USB_DRIVE, "Machine API Unreachable", category "hardware" / "system"), and there are no troubleshooting steps. Severity drives the start block, so a fallback can change behaviour. Question: should the built-in registry be generated from errors.json at build time (identical content), and is running with the fallback itself an alert condition? (§9.8)
OI-61 — Screen alerts do not auto-clear. The machine clears most codes by itself when the condition clears, but the Alerts screen keeps every alert until the operator dismisses it, and Start Cure on Home is blocked while any critical alert is on the screen — also when the machine has already cleared it (e.g. a sensor reconnected, a fan that recovered). Question: is operator acknowledgement of every critical intended, or should self-clearing machine codes leave the screen (or stop blocking Start Cure) when the machine drops them? (§9.6.2, §9.5.1)
OI-62 — Registry delivery, editable fields and layer values. The machine reads errors.json only at application start, from the installed application's config folder, so an edited message reaches a machine only with a software update. videoUrl is edited by the service team but is not listed in _meta.editableFields, and the layer values (daemon / backend / ui) describe the earlier stack. Questions: (a) what is the delivery path for registry edits to installed machines (software update only, cloud push, USB)? (b) add videoUrl to editableFields? (c) keep, redefine or drop layer for sCure CS? (§9.2, §9.9)
OI-63 — LED panel checks disabled in the shipped configuration. led_heating.enabled is false (decision 2026-09-16), so 9040–9045 are never raised and a panel that is not receiving current goes unnoticed during a cure. Two checks exist when enabled — a machine check on the Left / Right panels (90 s, 1.0 °C) and a Cure-screen check on all four panels (15 / 30 s window). Question: should LED checks be enabled for production, and if so which check(s) and thresholds apply? (§9.14.5)
OI-64 — Output watchdog trip leaves no alert. The output watchdog cuts the heaters and UV LEDs when the firmware heartbeat is silent for 20 s, but it only writes to the system log: after the firmware recovers or restarts, the operator, the cure report and sCure Cloud see no registry code. Question: should a watchdog trip be recorded and raised as a registry alert (new 9xxx code) after recovery / restart? (§9.14.7)

§10 Data & Persistence

OI-65 — Keep the optional PostgreSQL backend? sCure CS stores everything in JSON files on the unit by default; no shipped unit configuration (systemd units, installer, image, Origin package) sets DATABASE_URL, so PostgreSQL is never used in the field. When it is configured, the choice is made once at start-up and nothing is migrated between the backends (data written to the JSON files during a database outage stays there). Question: should the PostgreSQL backend remain a product requirement (and if so: device-local or central, who provisions it, access control / secrets, backup and migration between backends), or be dropped from the SRS and the product? (§10.1, §10.7)
OI-66 — Unbounded data files. Only the cure history has a retention limit (25 runs). phase_timings.json (one record per phase of every run), ui-alerts.json (dismissed alerts are kept forever), dev_events.jsonl and print_history.json grow without limit or pruning, and phase timings are kept for runs already pruned from the history. Question: what retention (count or age) is required for each of these, and should phase timings be pruned with their run? (§10.2)
OI-67 — No backup / export before a reflash. Reflashing the eMMC image erases all unit data (user programs, cure history and reports, component ON-time counters, LED calibration, settings incl. the serial number scanned at Setup). The unit has no data backup, export or restore, and the cloud receives only summaries (last 10 runs without telemetry, last 20 prints) and reports. Question: is loss of this data on reflash acceptable, or is a backup / restore (USB or cloud) required — at least for counters, calibration and serial number? (§10.5)
OI-68 — PostgreSQL backend stores less than the JSON backend. With PostgreSQL the telemetry table keeps only time, chamber temperature, UV on / type, four LED temperatures and fan RPM; heater PWM / on, target temperature, other sensors, fan duty, UV intensity / outputs, damper, nitrogen and door state are dropped, so the cure report built from that run is poorer. The cure-history view also takes the material name through print → job → material, but a run started on the unit is not linked to a print, so its material name is empty. Question: must both backends keep identical cure-run data (if PostgreSQL is kept, see OI-65)? (§10.7)
OI-69 — Interrupted run on the PostgreSQL backend. The JSON backend rewrites a run left running by a power cut to error at start-up; the PostgreSQL backend does not, so such a run stays running forever and can never be deleted (deletion skips running runs). Question: confirm DB-10 applies to both backends, and whether an interrupted run should be recorded as error or as a distinct status (e.g. "interrupted / power loss"). (§10.3, DB-10)
